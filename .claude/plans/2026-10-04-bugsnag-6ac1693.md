## Root cause

`updateReactions` reads and then writes in a `writer.transaction { pluck … update }` with no mode set (`Database+Conversations.swift:632`, unchanged at HEAD). With no mode, SQLite.swift uses `.deferred` (`Connection.swift:366`). Once a deferred transaction has read, a competing lock returns SQLITE_BUSY without consulting the busy handler, so the 2 s `busyTimeout` (`Database.swift:94`) never applies. The repo documents this hazard at `Database+Conversations.swift:304-306`. The app has a single writer connection (`DatabaseStore.swift:82`), so the other lock holder is inferred to be the notification extension, which opens a write connection for each push (`ExtensionStore.swift:74`). The fix doesn't depend on which connection held the lock.

## Proposed direction

Switch the transactions that read before writing to `writer.transaction(.immediate)` with the existing IMMEDIATE comment, as `:307`/`:408` do. That covers `updateReactions` (:632), `mergeReactions` (:650), and `upsertConversationMessages` (:390, whose `writeMessage` plucks first at :509). Don't route them through `Database.transaction`: it swallows errors (`Database.swift:167`).

## Risk

These writes are synchronous on `@MainActor`. Under extension contention, `apply` (one write per message, `ConversationReactions.swift:70-89`), send-message and load-older (`ConversationController.swift:1991`, `:1884`) can now wait up to 2 s per write instead of failing. `persistMessages` already waits like this. Today's cost is a reaction that stays stale until the next `refresh` (`ConversationReactions.swift:96`).
