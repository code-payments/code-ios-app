# Crash triage: EXC_CRASH (SIGKILL) — RUNNINGBOARD `0xdead10cc` (chat feed write)

**id:** `324AC8F1-2CC3-4E45-BF5B-8B66DADF7C8E` · **Source:** local TestFlight `.crash`
**Triaged:** 2026-10-01 · 1 report · iPhone17,1 · iOS 27.2 beta · launched 12:40:51, killed 13:03:33
**App version:** 2026.10.1 (570)
**Related:** `2026-09-20-crash-ffe0f684.md` — same kill, the `Session` poller path. That fix holds; this is a second writer it does not cover.

## Root cause

RunningBoard killed the process for being suspended while holding a SQLite write lock on the App Group store. The lock holder is `ConversationController.loadFeed(type:)`, not the poller.

`shutDownForBackground()` (AppDelegate.swift:184) takes a background assertion and drains only `Session`'s poller (`drainPoller()`, Session.swift:536) before closing the store. Nothing drains or gates `ConversationController`. Its feed loads are fire-and-forget `Task`s — `handleForeground()` (ConversationController.swift:560), `refetchAfterReconnect()` (:448), `start()` (:385) — that await `getDmChatFeed` on the network and then run a synchronous `BEGIN IMMEDIATE` transaction on the main actor (`replaceConversationFeed`, Database+Conversations.swift:300). If the fetch returns after `scenePhase → background`, the write runs with no assertion: either `database.close()` already ran and `Database.writer` reopens the store, or the close assertion has ended. Suspension lands inside the transaction → `0xdead10cc`.

Most likely trigger: a quick foreground → background bounce. `.active` fires `handleForeground()` → `Task { await loadFeed() }`; the user leaves before the feed RPC returns.

## Evidence

- Thread 0 (main) — `ConversationController.swift:852` → `persist` → `Database+Conversations.swift:300` (transaction) → `:316` → `:467` → `:482` (`writer.pluck(scoped)`) → `sqlite3Prepare`. Killed mid-transaction, lock held.
- `AppDelegate.swift:132-158` — `.background` notifies `session`, preferences, push, typing; `conversationController` gets no background call. No `didEnterBackground` / cancel hook exists on it (only `stop()` at :709, for logout).
- The transaction is long: per conversation it upserts, deletes and reinserts members, then `pluck`s the last message. The `pluck` goes through SQLite.swift's `columnNamesForQuery` → `expandGlob`, which prepares an extra statement per `SELECT *` (frames 21–22). That widens the window the lock is held, though it is not the cause.

## Fix (taken)

Guard every write rather than drain known writers — this is the second dead10cc from a writer nobody listed.

- `FlipcashStore/StoreWriteGuard.swift` — `StoreWriteGuard` protocol (`begin() throws` / `end()`), `.none`, `StoreWriteRefused`. Injected so `FlipcashStore` stays free of UIKit.
- `Database.write { writer in … }` is the only route to the write connection: the guard begins before the connection is touched (covering a reopen after `close()`), ends in a `defer` after COMMIT. The raw accessor is private to Database.swift, so the compiler proves every write site goes through it. All `Database+*.swift` writes, `transaction(silent:)`, `checkpoint()` and table creation are converted.
- `Flipcash/Core/Session/BackgroundStoreWriteGuard.swift` — one assertion shared by all writes in flight (nesting- and thread-safe), refuses with `StoreWriteRefused` when `beginBackgroundTask` returns `.invalid` or after iOS expires the assertion under in-flight writes. Off-main callers hop to main for `begin`; nested begins never do, so a thread inside a transaction never waits on main.
- `DatabaseStore` passes one shared guard to every store it opens; `ExtensionStore` and tests use `.none`.
- `shutDownForBackground()` keeps the poller drain, now only for the checkpoint.

Not taken: cancel-and-drain in `ConversationController`, and the `isCancelled` check after the feed fetch (a background write is now safe, just unnecessary).

Optional, separate: replace `writer.pluck(scoped)` with an explicit column select to drop the `expandGlob` round trip.

Open: whether an idle WAL connection with no transaction holds a lock that counts for dead10cc. Both crashes died mid-transaction, so there is no evidence it does.

## Verification

`FlipcashTests/Regressions/Regression_324ac8f1.swift` (6 tests): guard begins before `BEGIN IMMEDIATE` and ends after `COMMIT` on the crashing `replaceConversationFeed`; a refused write runs no SQL; a throwing body still ends the guard; nested writes share one assertion; no background time → refused; after expiry, refused until in-flight writes finish. Passing, along with the store suites and `Regression_ffe0f684` (130 tests).

## Risk

A write refused near suspension is lost locally; the store is rebuilt from server data, and feed/balance reloads run on every foreground. Off-main writers (rates) wait on main once per outermost write to begin the assertion.
