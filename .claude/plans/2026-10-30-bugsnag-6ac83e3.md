## ⚠️ Possible fix already in main

- `d3058c298` — fix(chat): close the mention picker on a cursor inside a Character (#1038) (touches `MentionTrigger.swift`). It shipped in 2026.10.3, and crashes continue on 10.3 (2) and 10.4 (2). It guards the app's *read* of the selection, not SwiftUI's write, so it does not address this crash.

## Root cause

Leading hypothesis. SwiftUI traps while it pushes the composer's `TextSelection` into the vertical text view. The stack is `TextViewAdaptor.updateUIView` → `UIKitTextInput.setSelection` → `uiSelectedRange.setter` (VerticalTextView) → `NSRange.init(_:in:)` → `String.UTF16View._offsetRange` → `_assertionFailure`. The only `selection:` binding on a text field is the composer's `TextField(..., selection: $composer.selection, axis: .vertical)` (`ConversationBottomBar.swift:1238`). It was added in `16f7f3baa` (#942), which first shipped in 2026.10.1, the "introduced in" build. The app already knows the binding "can pair a cursor with text it doesn't belong to for one layout pass" (`MentionTrigger.swift:46-47`). iOS 18 SwiftUI traps on that pair, and later iOS versions apparently don't.

## Evidence

- stack (all 20 events): no in-project frames. The top is `_NSRange.init<A,B>(_:in:)` ← `UIKitTextInput.setSelection(_:)` ← `TextViewAdaptor.updateUIView`.
- `device.osVersion`: 20/20 events and 7/7 users are on iOS 18.5–18.7.10. Users seen in the receiveCashLink and sweep groups split 10 on iOS 18 to 53 on iOS 26/27, so the zero crashes on 26/27 is not just a small sample.
- breadcrumbs: 19/20 end with `Began Editing Text > Stopped Editing Text > Began Editing Text > Stopped Editing Text`, and the last crumb is "Stopped Editing Text" in 11/20. Logs show the user inside an open conversation ("Suppressing chat push … reason=suppressedOpenConversation", 11/20).
- `ComposerModel.swift:176-258` sets `selection = nil` after every wholesale `draft` write. Send keeps focus (`isFocused = true`, `ConversationBottomBar.swift:1449`), so send does not explain the blur.

## Verification steps

On an iOS 18.x simulator, reproduce with a draft containing an emoji or another multi-UTF-16 character. Try three paths: blur after a mention insert (`ComposerModel.swift:275`), edit-then-cancel (`endEditing`, `:203`), and leaving the chat mid-draft. When one traps, write `FlipcashTests/Regressions/Regression_6ac83e33396a2e9520a308f4.swift` for that path.

## Proposed direction

Bind the field to a validating computed property on `ComposerModel` (say `fieldSelection`). Its getter returns `selection` only when its indices are valid for the current `draft` (`== endIndex` or in `draft.indices`), and its setter writes through. Then pass `$composer.fieldSelection` at `ConversationBottomBar.swift:1238`. SwiftUI never receives a stale pair, iOS 26 behaviour is unchanged, and the mention picker keeps mid-text detection everywhere. If the iOS 18 reproduction still traps with indices that are valid when read, SwiftUI is holding a copy of its own. In that case, fall back to passing `selection:` only on iOS 26+.

## Risk

The validating property touches only the composer field. The iOS 26+ fallback would cost iOS 18 users (about 16% of the users in this sample) mid-text mention detection.

## Expert input

- **/simplify**: no changes needed.
- **/swiftui-specialist**: its references have no `TextSelection` guidance. `dataflow.md` says to bind through a KeyPath, not a `Binding(get:set:)` closure, so the clamp belongs in a model computed property bound as `$composer.fieldSelection`, not an inline closure binding. That makes the version gate the fallback rather than the fix.
