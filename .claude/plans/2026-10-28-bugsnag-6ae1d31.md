## Leading hypothesis

The reconfigure exposed a desync. It did not cause one. Identity includes the cell class (`ChatItem+Differentiable.swift:17`, same at 10.2), and DifferenceKit only matches equal identifiers. So `items[i]` was already a `ChatMessageCell` item before this batch, while UIKit still showed a `ChatLinkMessageCell` at `i`.

Likely sequence:
1. A push drops a link card. By design that is a delete+insert (`ChatItem+Differentiable.swift:13-15`).
2. A second push reconfigures the same row while the first batch is still animating. `update(items:)` sets `isUpdating` (`ChatViewController.swift:532`) but never checks it.
3. UIKit resolves the reconfigure against the outgoing `ChatLinkMessageCell`.

*Not reproduced.* `FlipcashTests/Regressions/Regression_6ae1d311c6c10d79fa57232c.swift` runs this sequence and three variants on a 414×896 window with back-to-back pushes (link lost/gained then edited, link lost alongside an arrival, a link flipping twice). All four pass on HEAD (`2026.10.5`). `ChatTranscriptDiffFuzzTests` already pushes class flips without settling and also passes. After a batch commits, UIKit maps index `i` to the newly inserted cell, so overlapping batches alone don't reach the crash. The missing ingredient is something production has and the tests don't.

*Async resize and scroll position, also not reproduced.* The suite adds group-card rows whose lookup the test answers mid-animation (the card grows and invalidates its row), on a transcript scrolled to its middle. Two directed tests and a seeded churn (5 seeds × 40 rounds of class flips, edits, arrivals and card answers, a few task turns between pushes) all pass. A temporary probe checked every visible cell against its row after each push and after each answer: 400 checks, 0 mismatches. Remaining differences from production: SwiftUI-driven pushes (`updateUIViewController` timing), real link-card sources with cached answers (`known` non-nil on first paint), user scrolling or deceleration during the batch, and the reconnect burst.

*Production check.* `ChatViewController.logLiveCellMismatch(at:expected:)` logs `"Live cell class differs from its row"` at `.error` from `cellForItemAt`, only while `reconfigureItems(at:)` runs (bracketed by a new `reconfiguring` hook in `UICollectionView+Reload.swift`). Outside a reconfigure, `cellForItem(at:)` still returns the pre-batch cell: an ungated version fired 94 times across 21 passing chat tests. Gated, it ran 88 times and fired 0. Metadata: row, both identifiers, `isUpdating`, dragging/decelerating, distance from bottom, `hasPendingScroll`, `needsInitialScroll`. Crash events take `app_logs` from the on-disk tail (`ErrorReporting.swift:75`). An `.error` line forces a flush, but via `Task.detached` (`RotatingFileLogHandler.swift:155`) racing the abort, so the next crash *should* carry the line, not guaranteed.

## Evidence

- reason: "Dequeued reuse identifier: ChatMessageCell; Original reuse identifier: ChatLinkMessageCell". The existing cell carries two sets of `position`/`bounds.size` springs, so two batches were still in flight.
- stack (10.2 lines): `ChatViewController.swift:455` `spring.animate` → `UICollectionView+Reload.swift:53` `reconfigureItems` → `cellForItemAt :594` (`:676` at HEAD)
- log `[11:48:44] INFO flipcash.router`: "Push destination=tipConversation". The crash came 4s later, after the transport reconnected at 11:48:39.
- Reload paths don't leave stale cells. `:515` is followed by `flashAttention` (`layoutIfNeeded`, `:1128`) or `scrollToBottom` (`restoreContentOffset`). `UICollectionView+Reload.swift:39-41` uses the same restore unless no snapshot exists.
- `git log flipcash-2026.10.2..HEAD`: nothing touches update sequencing.

## Verification steps

Regression recipe: push `[text + linkPreview]`, then `[same, linkPreview: nil]`, then `[same, edited]`, all within one spring duration. Instrument `cellForItemAt`: when the existing cell's `reuseIdentifier` differs from `item.cellReuseIdentifier`, call `ErrorReporting.captureError` with both identifiers and `isUpdating`. Candidate fix: while `isUpdating`, hold the newest push and apply it on completion, mirroring `deferredItems` (`:488`, `:1793`).

## Risk

Every chat transcript. Queued pushes lag by up to one spring duration.
