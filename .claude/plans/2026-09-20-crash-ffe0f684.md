## Root cause

RunningBoard killed the process for holding a SQLite write lock at suspension. `Session`'s 10s poller has no lifecycle gate: `didEnterBackground()` stops the rates stream but never touches `poller` (Session.swift:501-514), and `Poller` cancels only from `deinit` (Poller.swift:30-32), so ticks keep firing once backgrounded. Each tick's `fetchLimits()` awaits the network (Session.swift:594), then opens a `BEGIN IMMEDIATE` write (Session.swift:599 → Database.swift:116) against the store in the App Group container shared with the notification extensions (StoreLocation.swift:21, ExtensionStore.swift:74). `closeDatabase()`'s background-task assertion covers only its own checkpoint (AppDelegate.swift:166-181), and `Database.writer` reopens the store on next access (Database.swift:44-50) — so the next tick undoes the close and writes with no assertion at all.

## Evidence

- thread 0 — `Session.swift:568` → `:589` → `:599` → `Database.swift:116` → `sqlite3_step` → `walFrames` → `guarded_pwrite_np`: killed mid-WAL-commit.
- `Termination Reason: RUNNINGBOARD 0xdead10cc` — documented as a file/SQLite lock held at suspension.
- `Poller.swift:22-26` — `while !Task.isCancelled { sleep; await action() }`; nothing feeds it scene phase.
- `Client+Transaction.swift:324` — bare `withCheckedThrowingContinuation`, no `withTaskCancellationHandler` (used elsewhere, e.g. SendCashOperation.swift:102). Cancelling the poller cannot interrupt an in-flight limits fetch: it resumes and falls straight into the synchronous write at Session.swift:599.
- `project.pbxproj:1034` — `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` and `Session` is unannotated (Session.swift:28), so the write runs synchronously on the main thread — matching thread 0.
- timing — launched 10:18:29, killed 11:57:50: ~1h39m, ~595 ticks.
- `git log` since the crash — only `d9e1e2e3` touches these files, and only to bump `schemaVersion`. Not a fix.

## Proposed direction

Gate the poller on scene phase the way the rates stream already is: cancel in `didEnterBackground()`, restart in `didBecomeActive()` (Session.swift:491-514). That removes the steady-state cause — a write every 10s for as long as the process survives backgrounded — but is provably insufficient alone, because the limits fetch ignores cancellation and no suspension point separates its return from the write. So the in-flight tick must also be drained inside the assertion `closeDatabase()` already holds (AppDelegate.swift:166-181), before it checkpoints; that also makes the checkpoint stick. Keep the drain at the app layer rather than asserting inside `Database.transaction` — `FlipcashStore` has no UIKit dependency, and `fetchBalance()` writes on the same tick (Session.swift:632, 639).

## Verification

`FlipcashTests/Regressions/Regression_ffe0f684.swift`: `didEnterBackground()` cancels the poller, and no `database.transaction` runs after it returns — observed failing first. Behaviourally, `Limits updated` (Session.swift:604) must stop appearing after `scenePhase → background` (AppDelegate.swift:128); today it appears every 10s.

## Risk

Touches session polling and the background path: limits/balance/flags stop refreshing while backgrounded, which is already the effective behaviour once iOS suspends. A wrong drain delays suspension rather than losing data.
