# Bugsnag 6ac06c5: unhandled crashes arrive without `app_logs`

Event `6ac06c50019af9e9256d0000` (error `6ac06c50396a2e9520f192ea`) carries only the
`app`/`device`/`error` metadata sections.

## Cause

- `recent_logs` is attached only inside the handled-error `Bugsnag.notifyError` callback
  (`Flipcash/Utilities/ErrorReporting.swift`, `capture`).
- `ErrorReporting.initialize()` registered no `addOnSendError`.
- `LogStore`'s ring buffer is in memory, so it is empty by the next launch, which is when
  Bugsnag (KSCrash) sends a crash report.

## Decision: previous-launch file tail, attached in `OnSendError`

Rejected: a `LogMiddleware` that calls `Bugsnag.leaveBreadcrumb` per line. It costs a
synchronous Bugsnag call on the logging thread for every `.info`+ line in Release, it puts
the logs in breadcrumbs instead of the `app_logs` section the handled path already uses,
and with `maxBreadcrumbs` unset it evicts Bugsnag's own state breadcrumbs.

Chosen:
- `LogTail.read(directory:maxLines:)` (FlipcashCore) reads the last lines of the newest
  `app-N.log` files, seeking to the last 64 KB of each instead of loading whole files.
- `LogStore.bootstrap` snapshots it into `LogStore.previousLaunchTail` before
  `LoggingSystem.bootstrap`, so nothing from this launch can append first. It also records
  `launchDate`.
- `ErrorReporting.initialize()` registers one `addOnSendError` that fills `app_logs` only
  when the section is absent, choosing by `ErrorReporting.logSource(...)`:
  - event time at/after launch → this launch's ring buffer (in-session app hangs);
  - event time before launch → previous-launch tail, unless the tail's newest file was
    written more than 60 s after the event (the tail belongs to a later launch: a crash
    report that failed to upload twice);
  - no event time → tail if `unhandled`, ring buffer otherwise.
  The tail's newest-file mtime is attached as `previous_launch_last_write` so a stale tail
  is visible.

### Deviation from the brief's "one path"

The handled-error `notifyError` callback keeps attaching the ring buffer. `OnSendError`
runs at upload time (`BSGEventUploadOperation`), and a handled event whose delivery fails
is stored and retried on a later launch — moving the capture into `OnSendError` would
attach the later launch's logs to it. The callback's metadata is stored with the event,
so the OnSend block sees the section and leaves it alone.

## Known gaps

- `FileWriteBuffer` flushes every 10 lines or on `.warning`+, and every flush is a
  `Task.detached`. Lines still buffered when the app dies are not on disk. A launch killed
  before its 10th line or first warning writes nothing, so a crash that early gets an empty
  tail (the simulator check's seeded first launch left no file content).
- `BSGEventUploadOperation` saves the pre-OnSend payload for retry. A crash report whose
  upload fails is stored without `app_logs`; if the retry happens on a later launch, the
  60 s check rejects that launch's tail and the crash goes up with no logs. A breadcrumb
  sink would survive this, at the per-line cost described above.
